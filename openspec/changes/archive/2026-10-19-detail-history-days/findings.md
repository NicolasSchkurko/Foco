Read-only audit of the change after the hardening commit, every `file:line` re-checked against the
real code by the parent. Classes: **(a)** requirement without an implementation · **(b)** implemented
behavior no spec describes · **(c)** a test that proves something other than what is declared ·
**(d)** opaque implementation.

The pass itself fixed nothing; the five items below were closed right after, by the corrections the
human asked for (tasks 7.1-7.5, same change). H1 and H2 changed code and the delta, so the change went
back to `applying` and re-ran its evidence (JVM suite, the two instrumented classes, the gate). The
`file:line` quoted in each item is the one the audit saw, before those corrections moved lines.

- [x] **(b) A failing store read is answered with a fallback, and neither the delta nor the living spec declares it.** `readOr` (`app/src/main/java/com/foco/app/ui/detail/AppDetailScreen.kt:282-290`, used at `:77` and `:87`) logs `Day read failed` and answers `emptySet()` / `emptyList()`, so a failed read and a day with no data are the same thing on screen, and the degrade carries no `[@test]`. — *Proposal:* either a delta scenario for the degraded read (which would need a way to force a store failure — the seam dropped in task 3.3) or a `known-gap` waiver naming the untested glue; today it is documented only as a limit in `walkthrough.md`. Human decides.
  **Resolved by task 7.1 — declared and tested, no waiver needed.** The auditor's "a delta scenario would need the dropped seam" was wrong: the helper itself is callable from a device test, no seam required. `readOr` is `internal` now (`AppDetailScreen.kt:291`) and `AppDetailReadTest` (device) proves both halves — a failed read answers its fallback, and `CancellationException` still propagates — while the delta carries the requirement *A failed stored read degrades instead of closing the app* with its `[@test]`. Nothing about the degrade is silent any more.
- [x] **(b) The stored-days window is read once at mount, so it can freeze a partial window.** `AppDetailScreen.kt:76-78` (`LaunchedEffect(Unit)`) reads the days while the startup backfill consolidates concurrently (`app/src/main/java/com/foco/app/MainActivity.kt:57` → `:82-85`, on IO). Opening the detail before the backfill finishes freezes the window at what the store already had (down to today alone, no back arrow) for the life of that screen instance; leaving and re-entering the detail re-reads it. No requirement says when the window must be fresh, while `proposal.md:24` expects the seven days to agree. — *Proposal:* a freshness rule (re-read the stored days when the screen resumes) or a `shortcut:` note with its upgrade trigger; it is not testable as JVM today. Human decides.
  **Resolved by task 7.2 — the window is re-read on every resume.** `AppDetailScreen.kt:80-87` reads the stored days inside `repeatOnLifecycle(RESUMED)` (`lifecycle-runtime-compose` was already a dependency, so nothing new was added). `AppDetailNavigationTest` pins it on device: a day seeded while the detail is open becomes reachable after the screen is resumed, and the walk back grows by exactly those days (`:139-155`). What stays: while the screen is never paused, the window is the one read at its last resume.
- [x] **(c) The device test asserts its premise instead of exercising it.** The scenario "A day the platform no longer serves" (`openspec/changes/detail-history-days/specs/usage-tracking/spec.md:28-30`) is evidenced by `app/src/androidTest/java/com/foco/app/ui/AppDetailNavigationTest.kt:109`, which seeds a synthetic day at `now - 3` (`:112-119`) and asserts the stored total, session row and disabled arrow (`:134-136`, `:143`); nothing proves `queryEvents` does not serve that day, yet `tasks.md:23` words it as "a stored day outside the platform window". What the test does prove holds: a past day is read from the store, not from the platform. — *Proposal:* correct the wording (`tasks.md:23` and the test KDoc at `:102-105`) or make the premise explicit; low. Human decides.
  **Resolved by task 7.3 — the wording now says what the test does.** The test's KDoc (`AppDetailNavigationTest.kt:104-107`) and task 4.2 state that the test seeds the day past the platform reader and exercises the store path; neither claims to prove the platform's answer. The scenario keeps its contract wording (the detail must not depend on the platform for a past day), which is the part the test does evidence.
- [x] **(c) The requirement declares only the two pure tests, while its screen-level claims are proven by an undeclared instrumented test.** `spec.md:13-14` declares `DaySelectionTest` (window) and `DetailDaySourceTest` (rule); "today read live and the previous days from storage" and "the arrows disabled at the ends" are proven only by `AppDetailNavigationTest.kt` (`:124`, `:131`, `:143`), which the requirement does not cite. — *Proposal:* add the instrumented test as a third `[@test]` line in the delta (a one-line spec edit); low. Human decides.
  **Resolved by task 7.4 — the requirement cites it.** `spec.md:15` now carries `[@test] app/src/androidTest/java/com/foco/app/ui/AppDetailNavigationTest.kt`, so every claim of the requirement is declared against a test (the resume walk kept the "arrow disabled at the oldest day" assertion, at the floor).
- [x] **(d) A name that says the opposite of what the value is.** `AvailableDays.kt:12` calls the window floor `oldestOffered` (`today - windowDays + 1`), while the *actually* oldest offered day is `oldest`, computed on the next line (`:13`); the `?: today` fallback makes the two read as interchangeable. — *Proposal:* a `kind: refactor` change renaming it to something like `windowFloor`; low. Human decides.
  **Resolved by task 7.5 — renamed in place.** `AvailableDays.kt:12` now reads `windowFloor`, which is what the value is; `oldest` (`:13`) keeps its name. It was a pure rename of a local inside this change rather than a separate `refactor` change, which would have re-opened a file this change already rewrites.
